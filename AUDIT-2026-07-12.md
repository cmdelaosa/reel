# tvtime — Production-Readiness Audit (2026-07-12)

**Question audited:** *Is this ready to deploy to Vercel and share with real friends without incident?* —
specifically multi-user security, unattended crons, free-tier limits, and day-one deploy gaps.

**Method:** 12 fresh-eyes finder agents (each blind to the others) → every finding re-checked by an
independent style-matched verifier (adversarial refuter for bugs/security, mechanical grep for dead
code, cost-arithmetic for optimizations, ADR-judge for design) → completeness critic → this synthesis.
Report-only; no code changed. **65 findings, 53 CONFIRMED, 11 kept at corrected (lower) severity, 1 refuted.**

---

## Executive answer

**Not yet — but the gap is operational, not structural.** The security *foundation* is genuinely
well-built: RLS is enabled on all 16 tables, cross-user read/write isolation holds, every
`SECURITY DEFINER` function pins `search_path`, the alerts dedup ledger is race-safe, and the metadata
cache is correctly service-role-write / public-read. No verifier could demonstrate one user reading or
corrupting another user's data through the SQL layer.

What blocks a clean launch is a cluster of **day-one plumbing gaps and silent-failure blind spots** that
would make the app *look* fine while quietly not working:

1. **The two daily cron jobs will never run on hosted Supabase** — nothing in the repo schedules them
   (only prose comments). Episode refresh and new-episode alerts silently do nothing forever. *(showstopper)*
2. **Alert emails go nowhere** — they're sent from Resend's test sender, which only delivers to your own
   inbox, and magic-link login rides Supabase's built-in mailer (rate-limited, team-addresses-only). Your
   friends would get neither login links nor alerts. *(showstopper)*
3. **The invite gate is client-side only.** Open signup + no server-side `is_invited` check means anyone
   who reaches the URL and clicks an emailed magic link becomes a real `authenticated` user. RLS still
   walls off *other people's* data, so this is a **cost/abuse + admission-control** hole, not a data
   breach — but it defeats the entire point of "invite-only." *(close before sharing)*
4. **Failures are invisible.** No telemetry anywhere; failed queries render as "you have no shows,"
   large imports hang forever, and a cron failing every day for a month reaches nobody.

None of these needs a rewrite. Most are a migration, a config toggle, or a small UI guard. The list below
is ordered so you can knock out the launch-blockers first.

## A. Launch blockers — fix before the URL leaves your hands

### A1. Nothing schedules the cron jobs *(HIGH — confirmed by 4 independent dimensions)*
`episode-refresh` and `alerts` exist only as edge functions. No migration enables `pg_cron`/`pg_net`,
stores the service key in Vault, or calls `cron.schedule`; the scheduling SQL lives solely as a header
comment (`supabase/functions/episode-refresh/index.ts:12-19`, `alerts/index.ts:11-12`). PLAN.md ticks
P2-C8 as *"scheduled episode-refresh job"* and ARCHITECTURE.md:227 calls it *"scheduled (daily)"* — both
false. **On hosted, both jobs never fire.** New episodes never get cached; no alert email is ever queued.
Nobody notices because there's no failure signal.
**Fix:** commit a migration (or a checklisted deploy SQL snippet) that enables the extensions, stores the
service key via `vault.create_secret`, and `cron.schedule`s both jobs ~30 min apart; verify post-deploy
with `select jobname, schedule from cron.job;` + a manual curl of each.

### A2. Alert emails and magic links won't reach your friends *(HIGH + MEDIUM — confirmed)*
- **Magic-link login** is the primary sign-in (`LoginPage.tsx:60`, `signInWithOtp`). On hosted Supabase,
  auth emails ride the *built-in* mailer unless custom SMTP is set — documented as test-only, a few
  emails/hour, and on newer projects **delivered only to project team-member addresses**. A friend's
  magic link silently never arrives. `config.toml`'s SMTP block is commented out and is local-only anyway.
- **Alert digests** are sent `from: onboarding@resend.dev` (`alerts/index.ts:30`), Resend's shared test
  sender, which **only delivers to the Resend account owner's email**. Every friend's alert is silently
  dropped by Resend.
**Fix:** configure custom SMTP in the hosted Auth dashboard using your Resend account from a verified
domain; change `EMAIL_FROM` to that domain; smoke-test a magic link + an alert to a non-team address
before inviting anyone.

### A3. Invite gate is client-routing only; signup is open *(HIGH↔MEDIUM — confirmed mechanism, severity debated)*
`config.toml:182` has `enable_signup = true`; no RLS policy, RPC, or edge function checks `is_invited()`.
`tmdb-proxy`, `importer`, and `export` authorize on `getUser()` alone. So anyone who loads the app, enters
an email, and clicks the magic link holds a valid `authenticated` JWT and can, with the public anon key:
loop `tmdb-proxy /search` (burning TMDB quota + service-role cache writes), fill the imports/avatars
buckets and the DB up to free-tier caps, and spam friend-requests to real handles. The comment in
`invited.ts:6-7` ("RLS remains the real wall") is misleading — RLS walls off *others'* data, not *un-invited
use*.
*Severity note (honest):* the adversarial verifier downgraded this from HIGH to MEDIUM because obtaining a
JWT requires a human clicking an emailed link (not a passive crawler) and **no cross-user data is exposed**;
the edge-functions verifier kept it HIGH on the cost/abuse surface. Both agree on the mechanism. Treat it as
**launch-blocking for an "invite-only" promise** regardless of the number.
**Fix (cheapest):** set `enable_signup = false` so a JWT can only exist for provisioned users — one line.
Defense-in-depth: also add `and public.is_invited((select auth.uid()))` to the WITH CHECK on the user-data
insert policies and a `is_invited` check in the three edge functions.

### A4. No hosted-provisioning runbook *(HIGH/MEDIUM — confirmed)*
The only remaining deploy checklist (P1-C5, `docs/phases/PHASE-1.md:80-85`) covers Vercel + auth redirects
and nothing else — not `supabase db push`, not `supabase functions deploy` (all 5), not `supabase secrets
set`, not the cron provisioning from A1. `app/vercel.json` and the storage-bucket migrations *are* present
(good), but the backend cutover is undocumented, so it's easy to deploy a frontend that talks to an
unprovisioned backend.
**Fix:** expand P1-C5 (or add P1-C6 "provision hosted supabase") into an explicit ordered checklist and run
it once end-to-end against the hosted project.

## B. Correctness & reliability — will bite soon after launch

### B1. Show status is derived from a systematically incomplete episode cache *(HIGH — confirmed)*
`deriveStatus`/`watchProgress` (`domain/status.ts:16-27`) consume counts from `rpc_library_rollup`, which
counts only **cached** episode rows. But following a show in-app upserts *seasons only*, never episodes
(`tmdb-proxy` `/title/:id` at `:390-397`); episodes are written only when you open a season tab, and the
cron backfills only the **latest two** seasons. So "3/10 watched," progress bars, and up-next are computed
against partial data for any show you didn't fully drill into. **Fix:** on follow (or in `/title/:id`),
fetch *all* regular seasons' episodes, or have the cron backfill titles whose cached episode count < sum of
`seasons.episode_count`; treat status as indeterminate until complete.

### B2. Large TV Time imports hang forever *(HIGH — confirmed by 3 dimensions)*
The importer stops at a 240s wall and leaves the job `status='running'`, expecting the client to
"re-invoke to continue" (`importer/index.ts:81,90-94`) — **but the client never re-invokes**
(`lib/import.ts:23-26` only polls), and `ImportPage.tsx:16` locks the upload UI while a `running` job
exists. Any non-wall rejection also leaves the job `running` with no `error` state. Realistic exports never
finish and the import screen is permanently stuck. **Fix:** wrap the background work in a final catch that
sets `status='error'`; auto re-invoke (the function is idempotent, zip kept until `done`) when
`report.done` stalls; add a staleness cutoff that unlocks the UI.

### B3. App-wide silent query failures *(HIGH — confirmed)*
Every data page destructures `data = []` + `isPending` and **never reads `isError`**, so after the 2
retries a failed load renders identically to "you have no data" (Shows, Tonight, Calendar, Explore,
History — verified sites in `silent-failures`). Auth gates fail the same way: a profile-query error is a
permanent blank page (`RequireOnboarded.tsx:10`); an `is_invited` error silently locks a real user out.
There is **no telemetry** (no Sentry), so persistent failures reach nobody. **Fix:** a shared "Couldn't
load — Retry" panel keyed on `isError`, and even a minimal error relay before inviting friends.

### B4. Fire-and-forget crons with zero observability *(HIGH→MEDIUM — confirmed mechanism)*
`episode-refresh` always returns 200 and only `console.log`s per-title errors inside a detached task; a run
where 100% of titles fail looks successful. Free-tier edge logs retain ~1 day. Combined with A1, a cron
could be broken for a month invisibly. **Fix:** write one `job_runs` row per run (ok/refreshed/errors) and
glance at it weekly, or ping a free dead-man's-switch as the last line of each function.

### B5. `max_rows = 1000` silently truncates several reads *(MEDIUM — confirmed across 3 dimensions)*
PostgREST caps result sets at 1000 (`config.toml:18`) and truncates *without error*. Affected:
`rpc_calendar_feed` (drops the future end of the calendar), per-title episode + watched-map queries for
long-running shows (`data.ts:64-71`, no pagination), the library rollup, and the `episode-refresh` title
list (`:155-165` — the cron only ever sees the first 1000 followed titles). *(Note: `export` and
`watch_history` correctly page past this — see "Checked & fine.")* **Fix:** paginate these reads in
1000-row ranges with a stable order (the `export` function is the reference implementation).

### B6. Alerts: any missed run permanently drops that day's notifications *(MEDIUM — confirmed)*
`pending_new_episode_alerts` only considers episodes aired in the last 24h (`0012:38-39`), and the ledger
is written *before* the email is attempted (`alerts/index.ts:83-93`). So a single missed/failed run (or a
downstream Resend failure after the ledger insert) means those episodes are marked "sent" and **never
alerted again**. **Fix:** widen the look-back or gate the ledger write on successful send; couple with the
A1/B4 scheduling + observability fixes.

### B7. Re-adding a stopped show leaves it hidden *(MEDIUM — confirmed)*
Re-following a previously-stopped show upserts without clearing `stopped` (`library.ts:98-101`), so the
show stays `stopped=true` and invisible in Tonight/Shows. **Fix:** include `stopped: false` in the
follow upsert.

## D. Tests — the riskiest gaps *(all confirmed)*

- **Zero tests for any of the ~38 RLS policies.** All authorization is RLS, yet no test exercises isolation
  between two users; the only e2e runs one seeded user through a happy path. A policy typo = a data leak
  with nothing to catch it. **This is the single most valuable test to add** (two users, assert B can't
  read/write A's rows). *(HIGH)*
- **Edge functions have no CI coverage at all** — `check.yml` only touches `app/src`; the four cron/import
  functions are never even `deno check`-ed. Add `deno check supabase/functions/*/index.ts` (~10s) and have
  the nightly e2e invoke `alerts` + `episode-refresh` once. *(HIGH)*
- Nightly e2e verifies mark-watched against the *optimistic UI only* (a broken `watch_events` write passes);
  invite gate, alerts dedup, and the importer parser (`lib.ts`, thousands of rows/user) have **zero**
  executions. *(MEDIUM)*
- CI has no production `build` check, and the e2e is nightly-only. *(LOW)*

## Checked and found solid (so the next audit doesn't re-flag these)

The finders were required to list risky-looking things they verified as **fine**. The strongest reassurances:

- **RLS is complete and correct.** All 16 tables have RLS enabled; owner-only `FOR ALL` policies pin
  `user_id = auth.uid()` in both USING and WITH CHECK; cross-user read/write isolation holds; metadata cache
  is service-role-write / public-read as intended; every `SECURITY DEFINER` function pins `search_path = ''`;
  `is_private` is honored in all four friend-read policies; the 0021 hardening (friendship immutability,
  `used_by` injection fix, friend-activity privacy) is sound.
- **Alerts dedup is genuinely race-safe** — ledger-first `upsert` with `ignoreDuplicates` + RETURNING makes
  duplicate emails impossible even under concurrent runs.
- **The scheduled functions can't be user-triggered** — both require the exact service-role key as bearer.
- **`trending_cache`/`popular_now_cache` are lazily refreshed inside user requests**, so a dead scheduler
  doesn't blank them; they're upsert-keyed so they don't grow unbounded.
- **Optimistic-update rollback is correct** (snapshot/cancel/restore, `optimistic` sentinel guards the
  in-flight race); **mark-up-to / Undo agree between TS and SQL**; **specials (season 0) are excluded
  everywhere**; **local-day/DST math is sound**.
- **`export` is the best-written function** — pages past `max_rows` with stable ordering, scopes to the
  caller via a user-scoped client (RLS), and neutralizes CSV formula injection.
- **Watch history is keyset-paginated** (truncation-proof); **DB 500MB headroom is comfortable** at stated
  scale; **edge-invocation volume is far below 500K/mo** (search debounced 300ms + cached).
- **`app/vercel.json` SPA rewrite exists**; **storage buckets are created by migrations** (no manual step);
  **dev auto-login is soundly gated** (`import.meta.env.DEV`, statically false in prod builds).

## Honesty appendix

- **Verification:** every finding was checked by an independent agent instructed to *refute* it (security/bugs
  at high effort), or grep-verify (dead code), or demand cost arithmetic (optimization), or judge against
  ARCHITECTURE.md/DESIGN.md (design). Counts: **53 CONFIRMED, 11 OVERSTATED** (kept at the verifier's corrected
  lower severity, correction noted inline), **1 REFUTED** (the `prototype/`/`scripts/` "dead code" claim —
  moved to F as not-dead). No finding in A–F rests on a single unverified agent.
- **Recurring mechanisms were deduped:** the invite gate (raised by 3 dimensions), cron scheduling (4),
  `max_rows` truncation (3), the Resend sender (3), and the stuck importer (3) each appear once above with
  the strongest evidence.
- **Completeness critic gaps, addressed:** the critic flagged the `export` function as unexamined — I read
  it directly (it's solid; see above). It also flagged the `logic-questioning` dimension as thin (3/4 items
  overstated, re-treading other dimensions) and named an untested logic surface **no dimension probed**:
  `ratings.ts`, `upnext.ts`/`mark_up_to`, `history.ts`/`watch_history`, `collections.ts`, `library_rollup`
  counting. These weren't audited for logic bugs and remain a known blind spot.
- **One check still worth running live (couldn't be done from code alone):** a **two-user cross-tenant RLS
  probe** on a local Supabase — seed users A and B, and as B attempt read/write on A's rows. RLS *reads* as
  correct, but with zero RLS tests nobody has *executed* the boundary, and it's the one place a mistake would
  be CRITICAL. Recommended as the first thing to do (and to keep as a regression test — see D).
